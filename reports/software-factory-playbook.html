The Software Factory Playbook

How to run an AI coding setup where agents do the building, machines do the checking, and you make the calls that matter. Written for one developer setting up a factory for personal projects, without wasting tokens or money.

01The short version

If you only read one section, read this one.

  1. A software factory is a pipeline, not a chatbot. Work moves through fixed stations: spec, plan, build, verify, review, merge. The agent works inside the stations. You stand at the gates.
  2. You don't get to chill, but you stop typing most of the code. Your job moves to the two ends: saying exactly what "done" means, and judging whether it is done.
  3. Machines verify, humans decide. Tests, linters and type checks run automatically inside the agent's loop and again in CI. You are asked questions only at real decision points, through a short "Decision Card" with at most three options.
  4. CI is the source of truth. An agent saying "all tests pass" is a claim. A green CI run on the pull request is evidence. Branch protection makes CI a hard gate.
  5. Instructions are suggestions; configuration is enforcement. Anything that would really hurt (deleting data, leaking secrets, touching production) is blocked by permissions, hooks and a sandbox, not by a sentence in a prompt.
  6. Start thin and custom, on top of Claude Code's built-in pieces. A short CLAUDE.md, three or four hooks, one CI workflow and a few skills. Add an open-source spec framework later only if you feel the pain it solves.

02Words you'll see

Nine terms carry the rest of this guide. Skim them now and come back when one shows up.

Agent
An LLM that can use tools (read files, run commands, edit code) in a loop until a task is done. Claude Code is an agent.
Harness
The program around the model that gives it tools, permissions and memory. Claude Code is the harness; Claude is the model.
CLAUDE.md
A Markdown file in your repo that Claude Code reads at the start of every session. Your standing instructions.
Skill
A folder with a SKILL.md recipe (for example "how we write specs"). Only its one-line description is loaded up front; the full text loads when needed. Cheap on tokens.
Subagent
A helper agent with its own fresh context. It does a side job (search the codebase, review a diff) and returns a short summary.
Hook
A shell command Claude Code runs automatically at a fixed moment, such as after every file edit or when the agent tries to finish. Deterministic: the model can't skip it.
MCP server
A plug-in that gives the agent extra tools (GitHub, a database, a browser). Every connected server adds tool descriptions to the context, which costs tokens.
CI
Continuous Integration. A clean machine (for example GitHub Actions) that runs your checks on every pull request.
Acceptance criteria
Testable statements of what "done" means, often in Given / When / Then form. The single most important input to a factory.

03What a software factory is

A repeatable system where AI agents carry work from an idea to a merged pull request, with automated checks at every step and humans at the decision gates.

The word "factory" is the point. A factory is boring on purpose: same stations, same checks, every time. That repeatability is what lets you trust the output without watching every keystroke.

04What makes a factory good

Six properties separate a factory that ships from one that produces confident-looking messes.

PropertyWhat it looks likeSmell when it's missing
Clear inputsEvery task has acceptance criteria before code starts.The agent builds the wrong thing very fast.
Small batchesOne issue, one branch, one PR you can review in 15 minutes.2,000-line PRs you approve without reading.
Verification firstFast checks run inside the agent loop; full checks run in CI; merges are blocked on red."It said tests pass" and they didn't.
Gates in the right placesYou decide the irreversible things. The agent decides the cheap, reversible ones and tells you.Either 40 questions a day or zero questions and a surprise schema change.

Rule of thumb

When the agent makes a mistake, prefer adding a check (a test, a lint rule, a hook) over adding a sentence to CLAUDE.md. A check is enforced every time and costs no tokens. A sentence is a suggestion the model may miss.

05Your role: do you get to chill?

No, but your work changes shape. You type less code and spend more time at the start (defining the task) and the end (judging the result).

Think of the agent as a fast, tireless junior engineer who never gets bored of running tests, sometimes misunderstands the brief, and will occasionally say something is done when it isn't. You wouldn't leave that person alone with production. You also wouldn't review every line they type.

The decisions that must stay with you

Use one test: how expensive is this to undo? If it's cheap, let the agent decide and tell you. If it's expensive, the agent must ask. Put this list in your CLAUDE.md:

  • What to build and what "done" means (the spec).
  • Database schema and data migrations.
  • Public APIs, URLs and anything other people depend on.
  • New dependencies and new paid services.
  • Authentication, permissions, secrets and anything security-related.
  • Deleting data, force-pushing, or deploying to production.
  • The final merge.

06Getting options without getting confused

Agents tend to either decide silently or bury you in an essay of possibilities. Fix both with one fixed format: the Decision Card.

The rules of the card:

  • One question, in one line.
  • At most three options. Recommended option first, marked clearly.
  • Two pros and two cons each. No more. Forces the agent to pick what actually matters.
  • Cost to undo: Low, Medium or High. This tells you how hard to think.
  • What happens if you just say "go": the default.

Here is what one looks like in practice:

Decision needed · Cost to undo: High

Where should we store user sessions for the new login flow?

A. Postgres table recommended

  • Uses the database we already run
  • Easy to revoke a session
  • One extra query per request
  • Needs a cleanup job

B. Redis

  • Very fast, built-in expiry
  • Common industry pattern
  • New service to run and pay for
  • Sessions lost if it restarts without persistence

C. Signed JWT only

  • No storage at all
  • Scales without effort
  • Hard to log a user out early
  • Easy to get the security wrong
If you say "go": I'll use A and add a migration in this PR for you to review.
Keep the questions rare

Add this to CLAUDE.md: "Ask me only when the answer changes what you'd do and the choice is costly to undo. Otherwise decide, and tell me in one line what you picked." Without it, you either get no questions or far too many.

07Guardrails: stopping the dumb stuff

You can't stop an agent from having bad ideas. You can make sure bad ideas either can't run, or get caught before they matter.

When people talk about "configuring the environment" for an agent, they mean layers of control around it. Some are soft: instructions the agent usually follows but can forget or misread. Others are hard: the agent physically can't do the thing, or is stopped automatically when it tries. Think of a new hire: the onboarding doc is soft, the badge that only opens certain doors is hard.

LayerQuestion it answersIn Claude CodeKind
ContextWhat does it know about how we work?CLAUDE.md, skillssoft
PermissionsWhat is it allowed to do?allow / ask / deny rules in .claude/settings.jsonhard
HooksWhat gets checked or blocked automatically?A PreToolUse hook that refuses a command before it runshard
SandboxIf it goes wrong, how much can it break?Sandbox mode, a container or cloud session, a separate git worktree, no production credentialshard
Code guardrailsDoes the change fit the expected shape?Type checker, lint rules, architecture tests, CI, branch protectionhard

How each layer helps

  • Permissions sort actions into three buckets: run freely (your check command), ask first (installing a package), never (reading .env, force-pushing). The settings file in Build yours, phase 3 has a starting set.
  • Hooks cover rules too specific for a permission list, such as "never edit migrations/" or "block any command containing DROP TABLE". The hook exits with code 2, the action is cancelled, and the agent is told why.
  • The sandbox is the real safety net, because pattern lists can be dodged. Block rm -rf and a determined agent may delete files another way. So also limit what it can reach: run it in Claude Code's sandbox mode, a container or a cloud session; give it no production keys; let it push only to branches, never to main.
  • Code guardrails make "the way we do things here" checkable: a type checker rejects wrong data shapes, a lint rule can ban raw SQL outside db/, and an architecture test (dependency-cruiser, ArchUnit) can stop UI code importing the database layer.
Two questions for any risky action

1. Can it happen at all? Say no with permissions and the sandbox where you can.
2. If it happens, how fast is it caught and how cheap is it to undo? Hooks catch it in seconds, CI in minutes, and working on branches keeps it reversible.

08Verification: the part that matters most

An agent saying "done" is a claim, not evidence. Verification turns claims into evidence, automatically, at several layers.

Your question: is it CI, or people asking questions?

Both, at different layers, for different jobs. Anything a machine can check (does it compile, do the tests pass, is there a leaked secret) is checked by a machine, first inside the agent's loop for speed and then in CI as the final word. People are asked only about things machines can't judge: is this the right thing to build, is this design sensible, is this risk acceptable. Machines verify; humans decide.

The six layers, from fastest to final

  1. Testable spec human

    Before any code · you + agent

    Every acceptance criterion must be checkable. "Login is fast" can't be verified. "Login returns in under 300 ms for a valid user" can. If you can't write the criterion as a test, the agent can't verify it either.

  2. Inside the agent loop

    Seconds · Claude Code hooks · every edit

    A PostToolUse hook formats and lints each file right after the agent edits it. A Stop hook runs your fast check command when the agent tries to finish; if it fails, the hook sends the errors back and the agent keeps working. This catches most mistakes before you ever see them, and the shell commands themselves cost no tokens. For UI and API work, also have the agent start the app and try the feature itself: click through it in a browser, or call the endpoint and read the response.

  3. Pre-commit

    Seconds · git hooks · every commit

    Secret scanning and formatting on commit. A cheap safety net for when hooks weren't running (for example when you edit by hand).

  4. CI: the source of truth

    Minutes · GitHub Actions · every PR

    A clean machine runs the full suite: build, type check, unit tests, end-to-end and API tests, dependency audit, security scan. With branch protection's "required status checks", nothing merges while it's red. CI can't be argued with, and it doesn't share the agent's assumptions about its own environment.

  5. AI reviewer

    Minutes · a second agent · on PR open

    A separate agent with a fresh context reads the diff against the acceptance criteria. This is the "maker and checker" idea: the writer is too close to its own work. Treat the reviewer as advisory. It's good at logic bugs and missing edge cases, but it's still an LLM and can miss things or invent problems.

  6. Your review human

    Minutes · you · before merge

    CI already proved it works. You check that it's right: matches the spec, sensible design, no scope creep, and the tests actually test the behaviour (see below). Use the short list in the checklist section.

  7. After merge

    Ongoing · preview deploys, smoke tests, monitoring

    For a personal setup a preview deploy and a smoke test are enough. Teams add error monitoring and one-click rollback.

The trap: the agent grading its own homework

If the same agent writes the code and the tests, the tests can quietly match the bug. Three defences, in order of effort:

  1. Tests from the spec first. Ask for the tests based on the acceptance criteria, check that they fail, then ask for the code. This is ordinary test-driven development, and it works well with agents.
  2. Read the test diff first in review. Deleted assertions, new skip markers or loosened expected values are red flags.
  3. Mutation testing (optional, later). Tools like Stryker or mutmut change your code on purpose and check the tests notice. It measures test quality, not just coverage.

Should an agent test the running product in CI?

Meaning: an agent that opens your app, clicks through a feature, or calls your API, and decides pass or fail. As of late 2026 this is emerging, not standard, and not used as a merge gate. The standard pattern is:

The pattern

The agent explores and writes the checks. Deterministic scripts enforce them in CI.

An agent makes a poor gate for four reasons. It isn't repeatable: two runs on the same build can give two verdicts, which is a flaky test. It can be confidently wrong ("the page looked fine"). It's slow and costs tokens every run, where a Playwright script costs nothing and finishes in seconds. And when it fails, you get a story instead of a line number.

For a backend, the scripted checks are API integration tests (real requests against a test server), contract tests that confirm the API still matches its OpenAPI spec (Schemathesis, Pact), and a few post-deploy smoke tests. If you try an advisory agent job, point it at a preview or test environment with test accounts, never at production.

What you can and cannot do

You can

  • Block merges until required CI checks pass.
  • Force the agent to run checks with hooks it cannot skip.
  • Feed failing output straight back to the agent so it fixes its own work.
  • Deny the agent access to files like .env or CI workflow files.
  • Add a second agent as reviewer on every PR.
  • Let the agent fix red CI on its own PRs.

You cannot (or shouldn't)

  • Trust the agent's own report that tests passed.
  • Treat AI review as a security gate on its own.
  • Verify something with no written expected behaviour.
  • Let the agent skip, delete or weaken tests to get green.
  • Give the CI agent production credentials or deploy rights.
  • Let untrusted people trigger the agent. Issue and PR text can carry prompt-injection attempts.

Industry practice in one list

  • Deterministic checks are the gate; LLM checks are advice.
  • Same checks run locally (in the loop) and in CI, from the same commands, so "works for the agent" means "works in CI".
  • Keep the fast check under about a minute so the agent can run it often.
  • Small PRs and required status checks. Teams also require a human approval; on a solo repo, skip that setting, because GitHub won't let you approve your own pull request.
  • Least privilege for agents: read-only by default, narrow write access, no production secrets.
  • Every escaped bug becomes a regression test.

09Running it without burning tokens

Most token waste comes from context, not from the code being written. Every turn, the model re-reads everything in its context window. Keep that window small and relevant.

Where tokens actually go

  • Long sessions. The whole conversation is resent each turn. Turn 80 costs far more than turn 5.
  • Reading too much. Dumping whole files or folders into context "just in case".
  • Always-loaded instructions. A 1,000-line CLAUDE.md is paid for on every single request.
  • Tool definitions. Each connected MCP server adds its tool descriptions to the context.
  • Retry loops. Vague tasks and slow feedback make the agent try, fail and try again.
  • The wrong model. Using the biggest model to rename a variable.

On a personal budget

  • Subscription vs API key. Interactive work on a Claude subscription has a predictable monthly cost. Pay-per-token API keys suit CI jobs. Compare both against how much you actually use.
  • Make CI agents opt-in. Run the AI reviewer on a label, not on every PR. Your deterministic CI still runs every time, for free or nearly so.
  • Spend the big model where it pays. Plan with the strongest model, then build and fix with the everyday one.

Prices change often, so this guide gives no per-token numbers. Check Anthropic's current pricing page when you size a budget.

10Custom or open source?

Build a thin custom setup on Claude Code's built-in pieces. Borrow ideas from open-source frameworks; adopt one wholesale only if it solves a pain you already feel.

Standards worth borrowing, whichever route you take

These are stable conventions, not frameworks. Adopting them costs nothing, and they make your projects easier to pick up again after months away.

  • Given / When / Then for acceptance criteria (from BDD). Each line maps to one test.
  • Architecture Decision Records (ADRs): a one-page Markdown file per big decision, in docs/adr/. Your accepted Decision Cards become ADRs.
  • Conventional Commits (feat:, fix:, …) so history is readable and changelogs can be generated.
  • AGENTS.md, the cross-tool instruction file other coding agents read. If you want tool independence, keep the rules there and have CLAUDE.md point to it.
  • Agent Skills (the SKILL.md format): an open format, so your skills are portable.
  • OWASP Top 10 as the checklist your AI reviewer uses for security.

11Build yours, step by step

Five phases. Each one is useful on its own, so you can stop after any of them. Examples use a Node project; swap the commands for your stack.

  1. One command that proves the code works

    Before any AI setup, make sure your repo has a single fast check command, for example npm run check, that runs lint, type check and unit tests in under a minute. Everything else in the factory calls this command. If it doesn't exist, ask Claude to create it; that's a good first task.

    Done whennpm run check passes on a clean clone and fails when you break something on purpose.

  2. CLAUDE.md: the factory's rulebook

    Short, specific, and focused on how you work together. Includes the Decision Card format and the "always ask me" list.

    Template CLAUDE.md

## Commands
- Install:      npm ci
- Fast check:   npm run check   # lint + types + unit tests, under 60s. Run after every change.
- Full tests:   npm test

2. Anything touching more than ~3 files: show me a plan first and wait for OK.
3. Write tests from the acceptance criteria first, confirm they fail, then implement.
4. One issue, one branch, one small PR.
5. Never skip, delete or weaken a test to get green. If a test looks wrong, tell me why.
6. "Done" means `npm run check` passes. Paste the last lines of its output.
7. After a UI change, start the app and try each acceptance criterion in the browser.

  3. Guardrails and hooks

    Four things: sort commands into allowed, ask-first and forbidden; block dangerous commands and protected paths before they run; format each edited file; and refuse to let the agent finish while checks fail. For the strongest protection, also run the agent in Claude Code's sandbox mode or a cloud session, and keep production keys off the machine entirely.

    Settings .claude/settings.json 
    {
  "permissions": {
    "allow": [
      "Bash(npm run check)",
      "Bash(npm test:*)",
      "Bash(git status)",
      "Bash(git diff:*)"
    ],
    "ask": [
      "Bash(npm install:*)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Edit(./.github/workflows/**)"
    ]
  },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash|Edit|Write|MultiEdit",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/guard.sh" }
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Edit|Write|MultiEdit",
        "hooks": [
          { "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs -r npx prettier --write --log-level silent" }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/verify.sh" }

      }

    Guard hook .claude/hooks/guard.sh

    Runs before every shell command and file edit. Pattern lists like this catch honest mistakes, not every possible route, which is why the sandbox matters too. Make it executable with chmod +x.

    #!/usr/bin/env bash
# Runs before Bash and file edits. Exit 2 cancels the action and tells the agent why.
input=$(cat)
cmd=$(echo "$input" | jq -r '.tool_input.command // empty')
path=$(echo "$input" | jq -r '.tool_input.file_path // empty')

if [ -n "$cmd" ] && echo "$cmd" | grep -Eqi 'rm -rf (/|~)|git push.*(--force|-f( |$))|git reset --hard|drop (table|database)'; then
  echo "Blocked: this command is on the dangerous list. Ask the user first." >&2
  exit 2
fi

case "$path" in
  */migrations/*|*/.env*)
    echo "Blocked: $path is protected. Ask the user first." >&2
    exit 2 ;;
esac
exit 0
    Stop hook .claude/hooks/verify.sh

    Exit code 2 tells Claude Code "not done yet" and sends the message on stderr back to the agent. Make the file executable with chmod +x.

    #!/usr/bin/env bash
# Runs when the agent tries to finish. Blocks it while the fast check fails.
input=$(cat)

# Already sent back once this turn? Let it stop. CI is the final gate.
[ "$(echo "$input" | jq -r '.stop_hook_active')" = "true" ] && exit 0

# No uncommitted edits and no commits ahead of main (just a chat answer)? Skip.
if git diff --quiet HEAD 2>/dev/null && [ -z "$(git log --oneline main..HEAD 2>/dev/null)" ]; then
  exit 0
fi

if ! npm run check --silent > /tmp/check.log 2>&1; then
  echo "Checks are failing. Fix them before finishing. Last output:" >&2
  tail -n 30 /tmp/check.log >&2
  exit 2
fi
exit 0

  4. CI gate and AI reviewer

    Two workflows: one deterministic gate that must pass, one AI reviewer that comments. Then turn on branch protection for main with the check job as a required status check, and turn on GitHub secret scanning with push protection. If the project has a UI or an API, add its end-to-end or API tests to the gate (have the agent write them from the acceptance criteria).

    Solo-repo settings

    Don't tick "require approvals" in branch protection: GitHub won't let you approve your own pull request, so every merge would be blocked. Required status checks are the gate that matters. Private repos get a limited number of free GitHub Actions minutes, so keep CI fast and cancel superseded runs.

    Deterministic gate .github/workflows/ci.yml 
    name: ci
on:
  pull_request:
  push:
    branches: [main]

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true   # don't pay for runs a newer push replaced

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run check          # same command the agent runs locally
      - run: npm test -- --coverage
      - run: npm audit --audit-level=high
    AI reviewer .github/workflows/ai-review.yml

    Uses Anthropic's official claude-code-action. Add ANTHROPIC_API_KEY as a repository secret. Input names change between versions, and the reviewer needs permission to post comments, so copy the tool settings from the code-review example in the action's README. The README also explains how to authenticate with a Claude subscription instead of an API key, which can be cheaper for personal projects.     name: ai-review

  5. Workflow skills and the learning loop

    Turn the stations into commands you can call: /spec drafts acceptance criteria from your notes, /plan produces a plan plus Decision Cards, /ship builds, runs checks and opens the PR. Add an issue template so every task starts with criteria. Then once a week, spend ten minutes asking: what went wrong, and which check would have caught it?

    Example skill .claude/skills/spec/SKILL.md 
    ---
name: spec
description: Turn rough notes or an issue into a short spec with testable acceptance criteria. Use before planning or coding any feature.
---

1. Read the issue or notes. Ask at most 3 clarifying questions, only if the goal is unclear.
2. Write the spec in this shape:

   ## Problem        (2-3 sentences, user's point of view)
   ## Acceptance criteria
   - [ ] Given ..., when ..., then ...     (each one testable)
   ## Out of scope
   ## Risk: low / medium / high, and why

3. Stop and wait for approval. Do not plan or write code yet.

A project session once it's running

Start: write two or three short issues, run /spec on each, fix the criteria. Approve plans and answer any Decision Cards. Let the agent build while you do something else. Later: review the PRs that are green, merge or send back. Once a week or so: a ten-minute retro on what went wrong.

12Checklist

Setup

  • A fast check command that runs in under a minute.
  • CLAUDE.md under 200 lines, with the Decision Card format and the "always ask" list.
  • Permissions: allow the check command, ask before installs, deny secrets and CI files.
  • Hooks: guard blocks dangerous commands, format on edit, Stop hook runs the check.
  • Agent runs in sandbox mode or a cloud session, with no production keys.
  • CI workflow running the same check command, set as a required status check.
  • Secret scanning and push protection turned on.
  • AI reviewer on PR open, capped turns.
  • Issue template with acceptance criteria.

Your 5-minute PR review

  • CI is green. If not, don't start reading.
  • Read the test changes first. Anything deleted, skipped or loosened?
  • Does each acceptance criterion have a test?
  • Anything outside the issue's scope? Send it back.
  • Anything from the "always ask" list that wasn't asked about?
  • Would you understand this code in six months?
