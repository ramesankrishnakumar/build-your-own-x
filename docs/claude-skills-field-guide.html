Building custom skills for Claude

Chapter 01

Start here: the mental model

Key ideaA skill is a folder of instructions and helper files that Claude reads only when the current task needs it. Think of it as the onboarding binder you hand a capable new hire: they already know how to work, but not your company's way of doing this one job.

You already know how to write a good prompt. A skill is a reusable, packaged prompt with three extra properties:

  1. It loads on demand. Claude sees a one-line summary of every installed skill. It opens the full instructions only when a task matches. You can install dozens of skills without filling up Claude's context window.
  2. It can carry files. Reference docs, templates and runnable scripts live next to the instructions. Claude reads or runs them when a step calls for it.
  3. It is portable. The same folder works in Claude Code, in the Claude apps (claude.ai and desktop), through the API and in the Agent SDK, with small differences covered in Chapter 4.

One fact matters most for the rest of this guide: a skill is not code that executes itself. Claude is the runtime. A skill only describes what Claude should do. Claude reads it and decides what to do next. Everything about triggering, handoffs and parallelism follows from this. A skill "calls" another skill only in the sense that its text tells Claude to go and load that other skill.

Chapter 02

How a skill loads: progressive disclosure

Key ideaSkills load in three layers. Each layer is read only if the previous one indicated that it is needed. This is why skill design is mostly about deciding what goes in which layer.
LEVEL 1 · ALWAYS LOADED

Name + description

From the YAML frontmatter. Sits in the system prompt for every request so Claude knows the skill exists and when it applies.

≈ 100 tokens per skill
LEVEL 2 · ON TRIGGER

SKILL.md body

The main instructions. Loaded when Claude decides the task matches the description.

aim for < 500 lines (a few thousand tokens)
LEVEL 3 · AS NEEDED

Bundled files

Reference docs are read only when a step needs them. Scripts are run, so only their output enters context, not their source code.

effectively unlimited
sequenceDiagram
    participant U as You
    participant C as Claude
    participant FS as Skill folder
    Note over C: System prompt already lists every skill's name and description
    U->>C: "Tailor my resume for this job post"
    C->>C: Description of tailoring-resume matches
    C->>FS: Read SKILL.md
    FS-->>C: Workflow steps
    C->>FS: Read references/ats-rules.md (step 2 asks for it)
    C->>FS: Run scripts/keyword_gap.py job.txt resume.md
    FS-->>C: Script output only (source never loaded)
    C-->>U: Tailored resume + gap report
One request moving through the three layers. Nothing in the folder costs tokens until Claude opens it.

What this means when you design a skill

  • The description does the triggering. Claude chooses skills based only on the name and description. If the "when to use" information is in the body instead, Claude never sees it at the moment it is deciding.
  • The body should be a map, not a manual. Put the workflow in SKILL.md and move detailed material into separate files that Claude opens only when a step needs them.
  • Scripts cost almost nothing. A 600-line validator costs zero context tokens if Claude only runs it. That is a strong reason to turn fragile steps into scripts.
  • Simple tasks may not trigger skills. Claude consults a skill when the task would benefit from it. A one-step request like "read this PDF" may be handled directly even when a PDF skill exists.
Chapter 03

Anatomy of a skill

Key ideaThe only required file is SKILL.md: YAML frontmatter (metadata) on top, Markdown instructions below. Everything else is optional and earns its place.
Folder layout
tailoring-resume/
├── SKILL.md              # required: frontmatter + workflow
├── references/           # read into context only when needed
│   ├── ats-rules.md
│   └── bullet-style.md
├── scripts/              # executed; only output enters context
│   └── keyword_gap.py
└── assets/               # used in output, rarely read
    └── resume-template.md
SKILL.md
---
name: tailoring-resume
description: Tailors a resume to a specific job posting by matching keywords,
  reordering experience, and rewriting bullets in a results-first style. Use when
  the user shares a job description, JD, posting or role link and wants their
  resume or CV adapted, even if they only say "make this fit".
---

# Tailoring a resume

## Workflow
Copy this checklist into your reply and tick items off as you go:
- [ ] 1. Extract requirements from the posting
- [ ] 2. Run the keyword gap check
- [ ] 3. Rewrite bullets
- [ ] 4. Validate against ATS rules

**Step 2.** Run `python scripts/keyword_gap.py job.txt resume.md`.
Treat any keyword it marks MISSING as a candidate, not an obligation: add it only
if the user's real experience supports it. Never invent experience.

**Step 3.** Follow `references/bullet-style.md` for bullet format.

**Step 4.** Check the draft against `references/ats-rules.md`. If any rule
fails, fix it and check again before showing the result.

## Output
Return the tailored resume using `assets/resume-template.md`, then a short
"What changed and why" list.

Frontmatter fields

The fields fall into two groups. The portable ones work on every surface. Claude Code adds extensions that control invocation and execution.

FieldWhereWhat it does
nameAllIdentifier. Max 64 chars, lowercase letters, digits and hyphens only. Cannot contain "anthropic" or "claude". In Claude Code it is also the /command name (defaults to the folder name).
descriptionAllWhat the skill does and when to use it. Max 1,024 chars on the API and claude.ai. This is the trigger.
allowed-toolsAllTools Claude may use without asking while the skill runs, e.g. Bash(git *).
license, compatibility, metadataAllInformational. compatibility is where you note required tools or packages.
when_to_useClaude CodeExtra trigger phrases appended to the description. Combined listing is cut at 1,536 chars, so put the main use case first.
disable-model-invocationClaude Codetrue means only you can run it (via /name). Use for actions with side effects: deploy, send, publish.
user-invocableClaude Codefalse hides it from the / menu, so only Claude loads it. Good for background knowledge skills.
argument-hint, argumentsClaude CodeArguments for /name arg1 arg2, substituted as $ARGUMENTS, $0, $1 or named $vars.
context: fork + agentClaude CodeRuns the skill in a separate subagent (e.g. Explore, Plan, or your own agent). Key for parallel work, see Chapter 8.
model, effortClaude CodeOverride model or reasoning effort for that turn.
disallowed-tools, hooks, paths, shellClaude CodeRemove tools, register hooks, only auto-activate for matching file globs, choose bash or PowerShell.
Portability trap. On claude.ai and the Skills API, only name, description, license, compatibility, metadata and allowed-tools are accepted. Any other key is a hard error. If you want one skill to work on every surface, use only those fields.

Two Claude Code power features

Arguments

---
name: mock-interview
argument-hint: [role] [company]
disable-model-invocation: true
---
Run a mock interview for the $0 role at $1. Ask one question at a time...

Typing /mock-interview backend-engineer Stripe fills in $0 and $1.

Dynamic context injection

A line like !`git diff --stat` runs a shell command before Claude reads the skill and replaces the line with the command's output. The skill then starts with fresh, real data in front of it. If the command fails, the whole invocation is aborted, so add || true to commands that are allowed to fail.

Chapter 04

Where skills live and run

Key ideaThe folder format is the same everywhere. What changes is where you put it and what the runtime around it can do, such as network access and installing packages.
SurfaceHow you installNotes
Claude Code~/.claude/skills/<name>/ (personal)
.claude/skills/<name>/ (project, commit it)
plugins: /plugin-name:skill		Precedence when names clash: enterprise > personal > project. Full frontmatter set. Old .claude/commands/*.md files still work and are now treated as simple skills.
Claude apps (claude.ai, desktop)Upload a zip in Settings → Capabilities / SkillsRuns in the code execution sandbox. Can install packages from npm and PyPI.

Do skills need to be referenced in CLAUDE.md?

Short answerNo. Claude Code finds skills automatically when they are in a skills folder (personal, project, nested or plugin). Each skill's name and description are already shown to Claude every session, so listing them in CLAUDE.md adds nothing for discovery.

CLAUDE.md is loaded in full every session, while a skill is loaded only when needed. If you copy a skill's content into CLAUDE.md, you pay for it on every request and end up with two copies that drift apart. Use CLAUDE.md for a pointer, never a copy, and only in these cases:

SituationMention it in CLAUDE.md?
A normal skill in .claude/skills/ or ~/.claude/skills/No. It is discovered automatically. If it isn't triggering, fix the description (Chapter 5), not CLAUDE.md.
A skill that must apply even when the request doesn't look like a matchYes, one line. Anthropic's own setup-writing-style skill does this. It notes that "skills are invoke-on-demand" and offers to add this line to ~/.claude/CLAUDE.md:
When drafting emails, messages, docs, or any prose meant to be sent or published as the user: first read ~/.claude/skills/my-writing-style/SKILL.md and follow it.
Two skills could both match and one should win in this projectYes, one line. For example: "For release notes, use /release-notes rather than general writing skills."
A user-only skill (disable-model-invocation: true)Optional. Claude can't run it, but a line like "To deploy, ask the user to run /deploy" lets Claude suggest it at the right moment.
A step that must happen every single timeNo, use a hook. Claude still follows CLAUDE.md using its judgment. Only a hook guarantees the step runs.

Outside Claude Code there is no CLAUDE.md. In the Claude apps you turn skills on in Settings. On the API you attach them to each request.

Chapter 05

Writing a skill well

Key ideaClaude is already very capable. A skill should add only what Claude cannot know on its own: your conventions, your data, your preferred defaults and your quality checks.

1. The description is the most important text you write

It must answer two questions: what does this do and when should Claude reach for it. Write it in the third person, because it is inserted into the system prompt. Include the words a user would actually type.

Weak

description: Helps with interviews.

Vague, no trigger words, and it competes with every other career skill.

Strong

description: Runs realistic mock technical interviews (system design, DSA, behavioral) and scores answers against a rubric. Use when the user wants to practice, rehearse or be quizzed for an interview, even if they just say "grill me on this".

Lean slightly "pushy". Anthropic's own skill-creator notes that Claude tends to under-trigger skills. Naming adjacent phrasings ("even if they don't say 'dashboard'") measurably helps.

2. Be concise: context is shared

For every paragraph, ask whether Claude really needs it. Do not explain what a PDF is or how Python imports work. A 50-token instruction with a code sample usually beats a 150-token explanation.

3. Match freedom to fragility

FreedomLooks likeUse when
HighPlain-language steps and heuristicsMany valid approaches, context decides. Code review, writing feedback.
MediumPseudocode, templates with parametersA preferred pattern exists but variation is fine. Report formats.
Low"Run exactly this script, no extra flags."Fragile or irreversible steps. Migrations, form filling, anything with a strict order.

Anthropic's analogy: on a narrow bridge with cliffs on both sides, give exact guardrails. In an open field, give a direction and trust the walker.

4. Explain why, not just MUST

"Never invent experience, because recruiters verify claims and a single false line can end the application" generalizes better than "NEVER INVENT EXPERIENCE". Claude follows reasons into situations your rules did not anticipate.

5. Give a default, not a menu

"Use pdfplumber. For scanned PDFs, use pytesseract instead." is better than listing five libraries. Each extra option is a decision Claude has to make, and some of those decisions will go the wrong way.

6. Smaller rules that prevent real bugs

  • Keep references one level deep. SKILL.md links to files directly. If a reference links to another reference, Claude may only preview the second one with something like head and miss content.
  • Add a table of contents at the top of any reference file over about 100 lines.
  • Use one term per concept. Don't alternate between "field", "box" and "input".
  • No time bombs. Avoid "before August use the old API". Put legacy material in a clearly labelled "Old patterns" section.
  • Say whether to run or read a script. "Run validate.py" and "See validate.py for the algorithm" lead Claude to do different things.
  • Use full MCP tool names like GitHub:create_issue when several servers are connected.
  • Forward slashes in all paths, even on Windows.
  • Scripts should handle their own errors. Catch the error and print a helpful message. Avoid unexplained constants: explain why the timeout is 30 seconds.
Chapter 06

Pattern catalog

Key ideaMost good skills combine two or three of these building blocks. Learn them as a vocabulary you can draw from.

Guide + references

SKILL.md gives a quick start and points to deeper files: "For form filling, see FORMS.md."

Use for: a single domain with a lot of detail.

Router (domain split)

SKILL.md picks a branch and loads only that branch's file: references/aws.md, gcp.md, azure.md.

Use for: several variants of the same job.

Checklist workflow

Numbered steps plus a checklist Claude copies into its reply and ticks off. This stops it from skipping steps.

Use for: any multi-step process.

Validator loop

Do the work, then run the validator. Fix and repeat until it passes. The validator can be a script or a style guide.

Use for: quality-critical output.

Plan → validate → execute

Claude writes a plan file such as changes.json, a script checks it, and only then is the plan applied.

Use for: batch, destructive or high-stakes changes.

Template

An exact output skeleton, either strict ("ALWAYS use this structure") or a flexible default.

Use for: reports, API payloads, documents.

Examples (few-shot)

Two or three input → output pairs show the style better than adjectives can.

Use for: commit messages, tone, formatting.

Script-backed

Deterministic steps live in scripts/. They are more reliable than code Claude writes on the spot and use no context tokens.

Use for: parsing, conversion, scoring.

Conditional workflow

"Creating new? Follow A. Editing existing? Follow B." There is a decision point at the top.

Use for: one skill that handles several intents.

User-only command

disable-model-invocation: true. Claude never runs it on its own initiative.

Use for: deploy, send email, submit application.

Background knowledge

user-invocable: false. Claude loads it automatically when relevant, and it stays out of the / menu.

Use for: house style, schema notes, conventions.

Orchestrator

A skill that writes no output itself. It splits the task up, sends the parts to subagents and combines their results. See Chapter 8.

Use for: research, large reviews, parallel work.

Chapter 08

Chaining, handoffs and parallel skills

Key ideaYes, a skill can hand over to another skill, and skills can run in parallel. But there is no built-in pipeline engine. Claude does the orchestration by following instructions you write, using the tools it has: the Skill tool, subagents and files. So you design workflows by writing clear instructions and clear handoff points.

The mechanisms available to you

MechanismHow it worksDeterminism
Instruction handoffThe last step of skill A says: "When the resume is done, use the drafting-cover-letter skill, passing out/resume.md." Claude loads B with its Skill tool.High if worded explicitly. Claude still decides, so name the skill exactly.
Stacking (Claude Code)You type /tailoring-resume /drafting-cover-letter job.txt. Both skills load in the same message, and each gets the arguments.High. You control it directly.
Forked skillcontext: fork runs the skill in its own subagent with a clean context. Its result comes back to the main conversation.High. Isolates the work.
Subagent with preloaded skillsA custom agent in .claude/agents/ lists skills: [ats-rules], so it starts with that knowledge already loaded.High. A reusable "specialist".
Parallel fan-outAn orchestrator skill tells Claude to start N subagents in one message, each with a brief. They run at the same time, and the orchestrator combines the results.Medium to high. Depends on how clearly you split the work.
HooksShell commands the harness runs on events (after a tool call, at session start, when Claude stops). Use them when a step must always happen.Fully deterministic. Not decided by the model.

Workflow A: sequential handoff (a pipeline)

flowchart LR
    U([Job post]) --> A[researching-company]
    A -- writes out/company.md --> B[tailoring-resume]
    B -- writes out/resume.md --> C[drafting-cover-letter]
    C -- writes out/letter.md --> D{{Review gate: you approve}}
    D --> E[/submit-application
user-only/]
Each skill reads the previous skill's file and writes its own. The final, irreversible step is user-only.

Three rules make a chain reliable:

  1. Pass state through files, not memory. Agree on paths like out/resume.md. A file is still there if the conversation gets summarized and can be read by a subagent that never saw the conversation. It also gives you something to inspect when a step goes wrong.
  2. Make the handoff a named step. "Step 5: invoke the drafting-cover-letter skill" works much better than "you might also want a cover letter".
  3. Gate the irreversible step. Make the final action disable-model-invocation: true so a person has to trigger it. A side effect: Claude cannot invoke that skill in the chain on its own, so the chain stops there and you run it.

Workflow B: parallel fan-out / fan-in

flowchart TB
    O[Orchestrator skill
splits the task] --> R1[Subagent 1
company + product]
    O --> R2[Subagent 2
engineering blog + stack]
    O --> R3[Subagent 3
interview reports]
    R1 -- notes/1.md --> W[Writer subagent
combines notes]
    R2 -- notes/2.md --> W
    R3 -- notes/3.md --> W
    W --> OUT([Prep brief])
Anthropic's own deep-research skill uses this shape: researchers run in parallel, then a separate writer combines their notes.

How to make this happen in a skill:

  • Ask for the spawns in a single message. "Spawn all researchers in the same turn" is what makes them run in parallel. Spawning them one by one runs them one after another.
  • Make subtasks independent and together complete. They should not overlap, and together they should cover the whole question. Overlapping briefs produce duplicate research. Gaps produce missing sections.
  • Keep each subagent's brief in a reference file (references/researcher.md). The orchestrator passes the file's path to the subagent. The orchestrator doesn't need to read that file itself, which keeps its own context small.
  • Collect results as files. Each subagent writes to its own path, and the step that combines them reads those files.
  • Remember that subagents don't see your conversation. A forked or spawned agent starts with only what you give it, so briefs must be self-contained.
An orchestrator skill (Claude Code)
---
name: researching-company
description: Builds an interview-prep brief on a company by researching it from
  several angles in parallel. Use when the user has an interview or application
  coming up and wants to understand a company, its stack, culture or interview loop.
---

# Company research (coordinator)

You coordinate. Do not research or write the brief yourself, so your context stays clean.

1. Create `research/$ARGUMENTS/notes/`.
2. In ONE message, spawn three subagents. Give each the path to
   `${CLAUDE_SKILL_DIR}/references/researcher.md` plus its angle:
   - product, business model, recent news
   - engineering blog, tech stack, open-source work
   - public interview experiences and the likely loop
   Each writes `research/$ARGUMENTS/notes/<angle>.md`.
3. When all three are back, spawn one writer subagent with
   `${CLAUDE_SKILL_DIR}/references/writer.md` and the notes folder.
4. Hand the user the brief, then offer: "Want me to run the
   tailoring-resume skill against this?"

Workflow C: router (one entry, many specialists)

flowchart LR
    Q([Practice request]) --> R{interview-coach
router}
    R -- system design --> S1[references/system-design.md]
    R -- DSA --> S2[references/dsa.md]
    R -- behavioral --> S3[references/star-method.md]
Inside one skill. Only the matching branch is loaded, so you get specialists without paying for all of them.

Choosing between them

  • Steps depend on each other's output: use a sequential handoff.
  • Steps don't depend on each other and each is large: fan out to subagents.
  • It's one job with variants: use a router inside a single skill. Don't build many small skills that compete for the same trigger.
  • A step must always run (formatting, a check, a log entry): use a hook, not an instruction.
Limits to know. Model-driven handoffs are probabilistic, so test them. Background forked subagents run with a narrower tool set. Parallel subagents can cost several times the tokens of one agent, so use them when the work is large enough to justify it. Don't create circular handoffs between two skills.
Chapter 09

Skills compared with the other building blocks

Key ideaEach building block answers a different question. Skills cover how to do this job. MCP covers how to reach that system. Subagents give a separate worker with its own context. CLAUDE.md holds what is always true in this project. Hooks cover what must always happen.
Building blockWhat it isWhen it is loadedReach for it when
SkillInstructions, files and scripts for a procedureOn demand, by description match or /nameYou keep re-explaining the same workflow or conventions
CLAUDE.mdAlways-on project memoryEvery session, in fullShort facts that apply to almost every task (build command, code style). It does not need to list your skills, see Chapter 4.
MCP serverA connection that gives Claude new tools (GitHub, Gmail, a database)Tool definitions are available all sessionClaude needs to access a system. A skill often teaches how to use those tools well.
SubagentA separate Claude instance with its own context, prompt and toolsWhen spawnedBig side tasks that would clutter the main context, or parallel work
HookA shell command the harness runs on an eventEvery time the event firesSomething must happen every time, regardless of what the model decides
Slash commandNow the same thing as a skill in Claude CodeWhen you type itUse a skill. Old command files still work.

These are usually combined. For example: an MCP server gives Claude Gmail access, a skill describes your follow-up email etiquette, a subagent drafts ten emails in parallel, and a hook logs every sent message.

Chapter 10

Testing and iteration

Key ideaWrite the tests before you write a lot of instructions. Without tests you are guessing what Claude needs. With them you can see where it actually fails.

The evaluation-driven loop

  1. Baseline: run 3 or more realistic tasks without the skill and write down exactly where Claude falls short.
  2. Write the minimum: only enough instruction to close those gaps.
  3. Compare: rerun the same tasks with the skill and compare against the baseline.
  4. Refine and widen: fix what broke, then add more test cases.

Test triggering separately

Ask two questions: does the skill do the job well, and does it activate at the right moments? For triggering, write about 20 queries:

  • Should trigger (8–10): different phrasings, casual and formal, including ones that never name the skill.
  • Should not trigger (8–10): near misses that share keywords but need something else. "Write a fibonacci function" is a useless negative test for a resume skill. "Review my LinkedIn headline" is a useful one.

Anthropic's skill-creator skill automates this. It runs each query several times, splits the queries into a training set and a held-out set, and proposes better descriptions.

Claude A writes, Claude B tests

Do a real task with one Claude session (A) and notice the context you keep supplying. Ask A to turn that into a skill. Then use it in a fresh session (B) on similar tasks. Bring B's mistakes back to A as specific notes, for example "B forgot to cap the resume at one page".

Watch how Claude navigates

  • A file is never opened: it's either unnecessary or not clearly referenced.
  • The same reference file is opened every time: move its content into SKILL.md.
  • Files are read in an unexpected order: your structure isn't as clear as you think.

Test with every model you'll use. Haiku may need more guidance, while Opus may find a long explanation unnecessary. Aim for instructions that work for all of them.

Chapter 12

Safety and sharing

Key ideaA skill can tell Claude to run code and use tools. Installing one is like installing software, so trust it the same way.
  • Only install skills from sources you trust, and read the scripts first. Watch for unexpected network calls or instructions to send data elsewhere.
  • No surprises. A skill should do what its description says and nothing else.
  • Never put secrets in a skill. Use environment variables or the platform's secret store.
  • Keep allowed-tools narrow, for example Bash(git diff *) rather than all of Bash.
  • Make side effects user-only (sending, deploying, submitting).
  • Share through version control: commit project skills to .claude/skills/, or package a collection as a plugin.
Chapter 13

The interview angle

Key ideaInterviewers asking about agents usually want to see that you understand context management, determinism vs model judgment, and how to evaluate. Skills are a clear example of all three.
"What is an Agent Skill, in one breath?"

A folder with a SKILL.md and optional scripts and references that packages a procedure for an agent. Only its name and description sit in context all the time. The rest loads when the task matches, so an agent can have hundreds of skills without paying for them in context.

"Why not put everything in the system prompt?"

Context is limited and shared. Every always-on token costs latency and money and competes for the model's attention. Progressive disclosure gives you a large library while paying only for what the current task uses.

"How is that different from MCP?"

MCP gives the agent new tools, meaning access to systems. A skill gives it a procedure, meaning how to do a job, often using those tools. They work together.

"How would you make a multi-step agent workflow reliable?"

Put the deterministic parts in scripts and hooks. Pass state through files with agreed paths. Add validation loops and plan-then-validate steps. Use human approval gates for irreversible actions. Measure with evals, including trigger evals with near-miss negatives.

"When would you run subagents in parallel?"

When the subtasks are independent and each is large enough to justify a separate context, as in research or multi-file review. The trade-off is token cost and the work of combining the results. Sequential work stays sequential.

Chapter 14

Checklist and glossary

Before you ship a skill

  • Description says what and when, in the third person, with the words users actually type
  • SKILL.md body is under ~500 lines. Detail lives in reference files one level deep.
  • Reference files over 100 lines start with a table of contents
  • Defaults instead of menus, consistent terms, no time-dependent claims
  • Multi-step work has a checklist. Quality-critical work has a validator loop.
  • Scripts handle their own errors and have no unexplained constants. Each script is clearly marked as "run" or "read".
  • Handoffs name the next skill exactly and pass state through files
  • Side-effect skills are user-only. allowed-tools is narrow.
  • 3+ task evals and about 20 trigger evals, tested on every model you'll use
  • Not copied into CLAUDE.md. At most, a one-line pointer for an always-on rule.
  • Frontmatter uses only portable fields if the skill must work outside Claude Code

Glossary

Context window
Everything the model can see in one request. It's limited, and every token in it costs money and attention.
Progressive disclosure
Loading information in layers, only when needed.
Frontmatter
The YAML block between --- lines at the top of SKILL.md.
Trigger
Claude deciding a skill applies, based on its description.
Subagent
A separate Claude instance with its own fresh context, given a task and returning a result.
Fork
Running a skill inside a subagent (context: fork) instead of the main conversation.
Fan-out / fan-in
Splitting work across parallel workers, then combining their outputs.
Hook
A command the harness runs automatically on an event. It's deterministic and not decided by the model.
MCP
Model Context Protocol, a standard way to connect tools and data sources to an agent.
Eval
A repeatable test case with expected behavior, used to measure whether a change helped.
